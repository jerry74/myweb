# Okinawa PWA 重設計規格

## 背景

目前 `okinawa-pwa/` 已具備可安裝的旅行 PWA 基礎，但畫面仍偏向資訊堆疊型頁面：

- 首屏雖有 hero，但核心決策資訊不夠集中
- 今日行程、餐食、雨天切換、住宿等內容分散
- 時間軸偏向長列表，旅途中快速查閱效率有限
- 視覺語言較接近通用資訊頁，尚未形成清楚的「旅行儀表板」體驗

本次重設計目標是把 `okinawa-pwa/` 改造成一個以「今天行程優先」為核心的沖繩旅行儀表板，讓使用者在旅途中能快速判斷下一步，並保留家人共同查看時所需的整體理解。

## 目標

1. 首頁在 3 秒內傳達今日最重要的行程資訊。
2. 首頁同時兼顧旅途中快速操作與家人共同查看的可讀性。
3. 以今天為預設焦點，只在需要時切換到其他天數。
4. 重做資訊層級、卡片結構與視覺語言，不改變既有行程資料本體。
5. 頁面在手機上優先成立，並保留桌面瀏覽的完整性。

## 非目標

1. 不新增後端、API、資料庫或登入功能。
2. 不改寫成 React、Vue 或其他框架。
3. 不新增即時天氣串接、定位或導航 API。
4. 不重做整個資料模型，只在必要範圍內調整欄位衍生與渲染方式。
5. 不處理 `myweb/` 或其他旅遊站點，範圍僅限 `okinawa-pwa/`。

## 核心設計結論

本次首頁採用 `Balanced Dashboard` 骨架，設計主軸是：

- 今天行程優先
- 兩者都要，但偏旅途中操作
- 保留旅程全局摘要，但不讓全局資訊壓過當日決策資訊

首頁資訊順序定義如下：

1. 今天主卡
2. 旅程摘要卡
3. 今日時間軸
4. 餐食與採買卡
5. 雨天切換卡
6. Day Tabs

這個排序的原則是先回答「現在要做什麼」，再回答「今天在整趟旅程的哪裡」，最後才提供支援型資訊。

## 資訊架構

### 1. 今天主卡

首頁第一屏的最大主卡，負責回答使用者最在意的 4 個問題：

1. 今天是第幾天、哪一天
2. 今天主題是什麼
3. 下一個關鍵行程是什麼
4. 可以立即做什麼操作

建議內容結構：

- `Day X`
- 日期、星期
- 今日主題
- 下一個關鍵行程
- 主操作列

主操作列預留以下 CTA：

- 查看今天時間軸
- 導航到下一站
- 查看雨天備案

今天主卡是整頁最高權重元件，必須明顯大於其他卡片，並在手機首屏內盡可能完整顯示。

### 2. 旅程摘要卡

這張卡不負責呈現所有全局資訊，只保留對當日判斷最有幫助的摘要：

- 目前 Day X / 共幾天
- 目前住宿
- 距離返程還有幾天
- 今天是否移動或換飯店

它的角色是全局狀態面板，協助家人快速理解今天在整趟旅程中的位置，並補充主卡沒有直接顯示的整體脈絡。

### 3. 今日時間軸

首頁預設只顯示今天的時間軸內容，不同日期透過 Day Tabs 切換。

每個時間節點改為獨立卡片，而不是長清單條目。每個節點卡包含：

- 時間標示
- 主要行程名稱或動作
- 簡短補充說明
- 外部連結按鈕
- 狀態標記

狀態標記至少支援：

- `雨天敏感`
- `可彈性調整`
- `固定行程`

目標是讓使用者快速掃讀後，能立即判斷：

- 這個節點重不重要
- 是否需要現在導航
- 若天氣改變，是否應調整

### 4. 餐食與採買卡

這張卡要從原本偏列表式資訊，轉成今日決策支援卡。

資訊優先順序：

1. 今天最需要處理的用餐選項
2. 今晚是否需要補貨
3. 哪些地點適合當補給點

呈現方式以短卡、標記與可點擊連結為主，避免長段敘述。

### 5. 雨天切換卡

雨天切換卡提升為首頁高優先支援卡，應使用決策語氣而非備註語氣。

每張卡至少包含：

- 今日下雨時如何改動
- 一句最短策略摘要
- `保留 / 取消 / 延後` 類型標記

這張卡的目的不是補充說明，而是作為旅途中臨場判斷工具。

### 6. Day Tabs

保留底部日期切換器，但重做成更像行程切換器，而不是偏技術風格的 tabs。

要求：

- 手機拇指友善
- 每個 tab 的點擊區充足
- 可快速看出目前選中的日期
- 切換時清楚同步更新今天主卡、摘要卡、時間軸與支援卡

## 視覺設計方向

整體視覺定位為：

**海島旅行感 + 儀表板效率**

需要避免兩個方向：

1. 通用 SaaS 介面感過強
2. 觀光宣傳頁式的過度裝飾

### 配色系統

建議採用：

- 主色：海風藍綠
- 背景：暖沙米白
- 強調色：珊瑚橘
- 中性文字：深藍灰
- 成功 / 穩定：綠色
- 提醒 / 雨天風險：橘色

設計原則：

- 讓畫面保有沖繩海島感
- 不依賴俗套的藍天白雲視覺
- 主色用於主卡、主要按鈕、關鍵高亮
- 強調色只用於提醒與決策資訊，避免全頁過度刺激

### 卡片層級

卡片分為 3 層：

1. 主卡：今天主卡，最大且最醒目
2. 支援卡：摘要卡、餐食卡、雨天卡
3. 節點卡：時間軸中的每個行程節點

三者必須在視覺重量、邊框、陰影與內距上拉出差異，避免每張卡片看起來等重。

### 文案風格

文案應偏短句與路標式語氣，例如：

- 今天去哪
- 下一站
- 今晚補貨
- 雨天改這樣

避免文章式長說明，優先支援快速掃讀。

## 互動原則

1. 首頁預設聚焦今天，不同日期由 Day Tabs 切換。
2. 主 CTA 必須在手機上容易點擊。
3. 所有互動卡片提供清楚 hover / tap 回饋。
4. 動畫只保留必要轉場與狀態回饋，不做裝飾性動效。
5. 需尊重 `prefers-reduced-motion`。

## 響應式原則

### 手機

- 以單欄為主
- 今天主卡置頂
- 摘要卡與支援卡垂直堆疊
- 時間軸卡片可快速掃讀，不依賴橫向空間
- 底部 Day Tabs 持續固定在底部或維持高可存取性

### 桌面

- 首屏可使用主卡 + 摘要卡雙欄配置
- 今日時間軸與支援卡之間保留清楚區塊感
- 不追求完全不同桌面版，主要是延展空間與資訊呼吸感

## 資料與程式設計原則

本次重設計盡量沿用既有 `days`、`stays`、`breakfasts`、`rainRules` 等資料來源，只增加必要的衍生邏輯，例如：

- 由 `activeDayIndex` 衍生今天主卡內容
- 從既有 schedule 推算下一個高優先節點
- 將餐食與採買資料重新分群為決策型區塊
- 將雨天規則映射到高辨識度卡片

避免為了視覺重做而過度拆散原始資料結構。

## 測試與驗證

### 功能驗證

1. 頁面仍可正常切換不同日期
2. 搜尋功能不失效，或在新設計中有等價保留
3. 安裝按鈕流程仍能正常運作
4. 外部連結可正常開啟

### 介面驗證

1. 手機首屏能看出今天主題與下一步
2. 今天主卡、摘要卡、支援卡有清楚層級
3. 時間軸不再像單純長列表
4. 雨天切換資訊在首頁容易被發現
5. 不產生水平捲動

### 體驗驗證

1. 在 375px 寬度下可舒適閱讀與操作
2. 在桌面寬度下不會因拉寬而失去視覺結構
3. 顏色對比與按鈕狀態清楚

## 成功標準

當以下條件成立時，視為本次重設計完成：

1. 使用者打開頁面後能立即理解今天重點。
2. 今天主卡、旅程摘要、時間軸、餐食、雨天切換之間有明確主次。
3. 首頁更適合旅途中快速使用，而不是只能靜態閱讀。
4. 畫面保有旅行感，但整體更像可實際上路使用的 PWA。
5. 不破壞既有資料內容與 PWA 基礎能力。
